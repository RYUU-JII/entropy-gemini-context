## Relational development model

V1 replaced G15 composition guidance. V2 introduced independent H1 development,
but coupled each territory to one scaffold followed by an ordered fan of twigs.
That produced the late upright repair shape identified by the user at seed
60746744. V3 removes that topology template. Historical dispatch modules remain
removed; there is no old-model runtime fallback.

Cloud geometry and the three existing form controls are retained for comparison.
Each cloud supplies a deterministic distributed demand in its oriented envelope
and depth. The compiler pools these sites and partitions them by spatial bearing,
independently of cloud identity. Multiple primary carriers may supply one cloud;
a primary carrier may supply several clouds. Cloud count is not branch count.
The three form controls remain meander, spreading and slant; natural, twin-trunk
and literati families have not been implemented by this change.

For each carrier, attachment selection uses aggregate demand height, inherited
trunk heading and spacing between primary junctions. At each prospective split,
the planner evaluates both child groups before committing the parent axis.
Candidate junctions vary in advancement and lateral position. Their costs include
future child opening, inherited heading change, transport length, desired-gap
intrusion and demand that the parent would overshoot. Downstream load weights
the exit heading. The chosen cubic distributes bending along the parent and
leaves both children attached to the same actual junction.

This is bounded local look-ahead over a hierarchical demand partition. It does
not optimize the whole graph simultaneously. The trunk intent is still authored;
resource competition, support mechanics, pruning/regrowth, whole-tree relays and
new form families are not implemented. Branch spacing/curvature can remain
regular, and projected crossings are not universally solved.

Branches do not snap a terminal endpoint onto an unreachable target. Demand
behind the inherited heading or with insufficient extension is recorded in
`program.unreached` with site ID and reason. Every demand site occurs exactly
once in either a terminal carrier or that unresolved ledger; ancestor axes retain
site membership for relational diagnostics. A cloud is a soft distribution, not
a hard occupancy guarantee. Current planning uses yaw .24 and real depth;
view-independent optimization is not established.

Floral allocation follows structural compilation. Actual terminal wood supports
organs at three stations. Local cloud density determines organ abundance;
flower paint cannot add a scaffold, pull a branch or move a completed node.
The normalized growth clock materializes a connected chronological prefix,
interpolates the current tip, and thickens wood using age and downstream mass.
Growth 1 completes wood and flower maturation; partial bloom caps openness.
Bloom controls do not alter structural identity.

`strength` remains gap priority; zero still plans the crown. `room` changes cloud
distribution extent, which affects real branch planning and floral allocation.
Exact new source identity binds these semantics. The request/receipt envelopes
remain v1; internal plan, program, graph and scene contracts are v3. Old receipts
cannot silently replay under the new model.

## Preservation and verification

The build validates the frozen source pin and writes only H1 artifacts. It stages
complete bundle and manifest files and renames them into place, publishing the
manifest last. This avoids truncating a file while the loopback host is reading
it. This is not a two-file atomic transaction: concurrent source checks can fail
visibly during publication and must be reloaded after build completion.

Reference graph and paint parity are verified against the original executable
in a separate Node worker. The common camera may reframe A when H1 bounds change;
reference generation and paint policy stay identical at the same bounds.
Product storage, learned preferences, seed rejection, training and automatic
promotion are outside H1. Missing or mismatched source/receipt identity fails.

Verification protects shared cloud/carrier relations, complete demand accounting,
forward child departure, connected taper and timing, mature organs, deterministic
prefixes, independent bloom, common camera, actual controls and exact receipts.
Short-lived HTTP and jsdom checks cover source routes and controller flows.
Native Canvas captures are visual evidence, not browser QA or aesthetic PASS.
