# Refactoring Playbook (Entropy MV3)

- Scope: 전체 코드베이스 (`src/`, `tests/`, 빌드/런타임 경로)
- Last Updated: `2026-04-03`

- Status: Active
- Owner: repository governance
- Last validated against code: 2026-04-03
- Path policy: current-only
- Canonical for: refactor sequencing, cutover discipline, and deletion-first cleanup rules

## 1. 목적
이 문서는 "지금 리팩터링이 필요한가"를 빠르게 판정하고,
리팩터링을 한다면 무엇을 어떤 순서로 바꿔야 하며,
최종적으로 어떤 상태에 도달해야 하는지를 명확히 정의하는 실행 기준서다.

핵심 원칙은 세 가지다.

1. 동작 안정성 보존
2. 복잡도 감소
3. 향후 변경 비용 절감

## 2. 리팩터링 정의 (이 문서에서의 의미)
리팩터링은 "기능 요구사항을 바꾸지 않고 내부 구조를 개선하는 작업"이다.
아래는 리팩터링이 아니다.

1. 새 기능 추가
2. 제품 정책 변경
3. UI/UX 의도 자체 변경

리팩터링의 목표는 코드 미학이 아니라 운영 가능성이다.
즉, 버그 가능성을 줄이고, 변경 난이도를 낮추고, 성능/테스트/관측 가능성을 올려야 한다.

## 3. 리팩터링 필요 여부 판정 기준
아래 항목 중 2개 이상이 반복된다면 리팩터링을 "필요"로 본다.

1. 변경 리드타임 악화
   - 작은 요구사항도 수정 파일이 과도하게 많다.
   - 한 함수/컴포넌트 수정 시 연쇄 수정이 자주 발생한다.
2. 결합도 과다
   - 모듈 경계를 넘는 직접 참조가 많고 순환 의존 위험이 있다.
3. 중복 증가
   - 같은 규칙/로직이 여러 파일에 복제되어 버그 수정이 누락된다.
4. 테스트 신뢰도 하락
   - 회귀가 반복되거나, 테스트가 구현 세부사항에 과도하게 묶여 있다.
5. 의미 불명확
   - 파일/함수 이름과 실제 역할이 다르고, 호출 흐름 추적이 어렵다.
6. 성능 병목 반복
   - 동일 종류의 렌더/스토리지/연산 문제가 재발한다.
7. 온보딩 비용 과다
   - 신규 작업자가 구조를 이해하는 데 지나치게 오래 걸린다.

정량 보조 신호(권고):

- 동일 버그 클래스 재발 횟수 증가
- 한 PR의 영향 파일 수/라인 수가 꾸준히 커짐
- 핫스팟 파일에 변경 집중

## 4. 리팩터링 보류/금지 기준
아래 상황에서는 대규모 리팩터링을 보류한다.

1. 출시 임박, 회귀 비용이 수용 불가능한 시점
2. 문제를 설명하는 재현 케이스/테스트가 없는 상태
3. 목표 아키텍처 합의 없이 "일단 갈아엎기" 접근
4. 측정 지표 없이 감각만으로 진행

원칙: "측정 불가한 리팩터링은 예술이고, 운영에서는 위험".

## 5. 우선순위 프레임워크 (무엇부터 바꿀지)
우선순위는 아래 순서로 결정한다.

1. 사용자 체감 장애/회귀 위험이 큰 영역
2. 변경 빈도가 높은 핫스팟 경로
3. 결합도/중복으로 인해 생산성을 갉아먹는 공통 경로
4. 마지막으로 국소적 미관 개선

점수화 규칙(간단):

- `Priority Score = (Impact x Frequency x RiskReduction) / Effort`
- 점수가 높은 순으로 배치

의사결정 질문 4개:

1. 이 변경이 회귀 확률을 실질적으로 낮추는가?
2. 다음 3개월 변경 비용을 낮추는가?
3. 테스트 가능성을 높이는가?
4. 롤백이 쉬운 단위로 쪼갤 수 있는가?

## 6. Entropy 프로젝트 가드레일 (기본 준수, 예외는 근거 필요)
리팩터링 중 기본적으로 아래 규칙을 따르되, 예외가 필요한 경우 PR에 배경/영향/롤백 계획을 남긴다.

1. 테마 Canonical ID 고정
   - 허용: `matrix`, `entropy`, `cyberpunk`, `clinical`, `scp`, `zen`
2. 테마 ID 정규화는 기본적으로 `normalizeThemeId` 사용
   - 파일: `src/themes/core/ids.js`
3. 레거시 테마명 처리 원칙
   - 런타임/스토리지/문서의 최종 값은 Canonical ID (`matrix`, `entropy`, `cyberpunk`, `clinical`, `scp`, `zen`)로 수렴
   - 입력 호환이 필요하면 경계 adapter에서만 alias를 수용하고 내부로는 즉시 canonicalize
4. 테마 엔진 접근 경로 고정
   - Behavior/Layout: `src/themes/core/profile.js`
   - Theme registry/loading: `src/themes/core/registry/index.js`
   - Theme plugin catalog: `src/themes/core/runtime/pluginCatalog.js`
5. Zen 테마 프로토콜
   - 일본식 Zen 콘셉트(karesansui/chaniwa)를 기본 축으로 유지
   - 실험적 확장(혼합 모티프/네이밍)은 feature flag 또는 독립 실험 경로에서 허용
6. 데이터 프라이버시 원칙
   - 사용자 데이터 외부 전송 금지 (device-local only)
7. Zustand 5 셀렉터 규칙
   - 객체/복수 키 셀렉터는 `useShallow`를 기본값으로 사용하고, 예외는 측정 근거를 남긴다.
8. 저장소 경계
   - 고용량 통계: `StatsAggregateStore` + IndexedDB bucket stores
   - UI 설정: `chrome.storage.local`
9. 네이밍 규칙
   - 컴포넌트: PascalCase
   - 로직/스토리지 키: camelCase
   - 저장 키: snake_case
10. 구조 위반을 숨기는 fallback 금지
   - active runtime/storage/theme path에는 새 fallback을 추가하지 않는다.
   - canonical owner/path가 깨지면 explicit failure로 surface하고, 필요 시 migration이나 documented degraded mode로 분리한다.

## 7. 리팩터링 실행 절차 (실무 표준)
1. Baseline 고정
   - 현재 동작을 스냅샷/테스트/로그로 먼저 고정한다.
   - "무엇이 동일해야 하는지"를 먼저 명문화한다.
2. 경계 설정
   - 이번 작업의 In-Scope / Out-of-Scope를 문서로 박는다.
3. 작은 단위 분해
   - 파일 이동/이름 변경/의존성 역전/중복 제거를 분리 커밋한다.
4. 안전장치 선행
   - 리팩터링 전 테스트(또는 회귀 방지 테스트)를 먼저 추가한다.
5. 기계적 변경 우선
   - 의미 변화 없는 변경(이름/모듈 경계/추출)부터 처리한다.
6. 구조 변경 적용
   - 의존 방향 단순화, 책임 분리, 상태 경계 정리를 수행한다.
7. 검증 및 회귀 점검
   - 빌드 + 핵심 테스트 + 수동 시나리오 점검을 수행한다.
8. 결과 문서화
   - 무엇이 쉬워졌는지/남은 위험/후속 과제를 기록한다.

## 8. 설계 원칙 (내가 리팩터링할 때 항상 보는 기준)
1. 명시적 경계 우선
   - "어디까지가 이 모듈 책임인가"를 코드 구조에 드러낸다.
2. 데이터 흐름 단방향화
   - 상태 원천을 줄이고 파생값은 계산으로 만든다.
3. 정책과 메커니즘 분리
   - "무엇을 할지"와 "어떻게 할지"를 분리한다.
4. 시간 의존성 고립
   - 시간/랜덤/외부 I/O는 어댑터로 감싼다.
5. 실패를 기본값으로 설계
   - 에러 경로와 복구 경로를 1급 흐름으로 취급한다.
6. 구조 위반은 숨기지 않는다
   - fallback으로 "일단 동작"시키기보다, invariant break를 loud failure로 surface해야 장기 비용이 줄어든다.
7. 가독성은 미래 비용 절감 장치
   - 짧은 코드보다 "오해 없는 코드"를 우선한다.

## 9. 코드 레벨 체크포인트
리팩터링 PR마다 아래를 점검한다.

1. 함수
   - 한 함수가 한 책임을 가지는가?
   - 입력/출력이 명확하고 부수효과가 드러나는가?
2. 모듈
   - import 그래프가 단순해졌는가?
   - 순환 의존 위험이 제거되었는가?
3. 상태 관리
   - store shape가 최소화되었는가?
   - 선택자 재렌더 비용이 통제되는가?
4. 스토리지
   - 데이터 성격에 맞는 저장소를 쓰는가?
   - 직렬화/마이그레이션 경로가 안전한가?
5. UI/테마
   - canonical theme id 경로가 깨지지 않았는가?
   - 레거시 alias 수용이 경계 계층으로 한정되어 있는가?
6. 테스트
   - 구조 변경이 테스트 취약점으로 숨지 않았는가?
   - "동작 계약" 중심 테스트가 보강되었는가?

## 10. 완료 조건 (Definition of Done)
아래를 모두 만족하면 리팩터링 완료로 본다.

1. 동작 동일성
   - 사용자 관점의 기능 계약이 유지된다.
2. 복잡도 감소
   - 책임 경계가 명확해지고 중복/결합이 줄었다.
3. 검증 통과
   - `npm run build` 성공
   - 관련 테스트 통과
4. 운영성 개선
   - 장애 원인 추적이 이전보다 쉬워졌고, 구조 위반이 silent fallback으로 숨지 않는다.
5. 문서 동기화
   - 변경된 구조/규칙이 문서에 반영되었다.

## 11. 리팩터링 시작 전 체크리스트
- [ ] 이 작업이 기능 변경이 아니라 구조 개선인지 확인
- [ ] 문제 재현 경로/증거(테스트, 로그, 사례) 확보
- [ ] Baseline 테스트 또는 회귀 방지 테스트 준비
- [ ] In-Scope/Out-of-Scope 명시
- [ ] 롤백 가능한 단계로 작업 분해

## 12. 리팩터링 종료 후 체크리스트
- [ ] `npm run build` 통과
- [ ] 영향 범위 테스트 통과
- [ ] 테마/스토어/스토리지 규칙 위반 없음
- [ ] 중복/결합/가독성 측면 개선 근거 기록
- [ ] 후속 과제(남은 부채) 명시

## 13. 안티패턴 (주의할 패턴)
1. 테스트 없이 대규모 파일 이동
2. 리팩터링과 기능 추가를 한 PR에 혼합
3. 이름만 바꾸고 의존 구조는 그대로 둠
4. 레거시 alias를 무기한 방치해 canonical 수렴 계획이 사라지는 상태
5. 구조 문제를 fallback으로 덮어 "일단 돌아간다"를 성공으로 착각하는 상태
6. 성능 이슈를 추측으로만 해결

## 15. 결론
좋은 리팩터링은 "코드를 새로 쓰는 일"이 아니라
"미래 변경의 실패 확률을 체계적으로 낮추는 일"이다.

이 문서를 기준으로,
- 필요성은 증거 기반으로 판단하고,
- 우선순위는 영향과 위험 감소 중심으로 정하고,
- 완료는 빌드/테스트/운영성으로 검증한다.

이 세 가지가 지켜지면 리팩터링은 취향이 아니라 생산성이 된다.
